# product_product

## Source system
The table originates from Odoo (formerly OpenERP), an open-source ERP system. The naming convention `product_product` (representing product variants) paired with `product_tmpl_id` (the product template) and the specific sequence-based ID generation is characteristic of the Odoo ORM architecture.

## Functional process 
This table supports the product catalog and inventory management process. It manages individual product variants (e.g., a specific size or color of a base product) within the inventory, tracking physical attributes like weight and volume, as well as identification codes like barcodes and internal references.

## Description
One row in this table represents a single, unique product variant within the Odoo product catalog. It serves as a raw landed copy of the variant-level data, acting as the primary source for downstream inventory and sales reporting. The grain is one row per unique product variant.

## Keys

- **Primary key (inferred):** `id`
- **Foreign keys (inferred):** 
    - `product_tmpl_id` → `product_template.id`: This column links the variant to its parent product template, which defines shared attributes.
    - `create_uid` → `res_users.id`: References the user who performed the creation.
    - `write_uid` → `res_users.id`: References the user who performed the last update.
- **Natural keys (inferred):** 
    - `default_code`: Often used as the unique SKU in business operations.
    - `barcode`: Globally unique identifier for retail/logistics.

## Caveats for downstream consumers

- **Sensitive Data:** No direct PII, but `create_uid` and `write_uid` link to user tables which may contain employee information.
- **Timestamps:** Assumed to be in UTC, as is standard for Odoo PostgreSQL databases.
- **Soft Deletes:** The `active` column acts as a soft-delete flag; queries should generally filter by `WHERE active = TRUE` unless performing historical analysis.
- **JSONB:** `standard_price` and `lot_properties_definition` contain semi-structured data; ensure your SQL dialect supports `->>` or `jsonb_extract_path_text` for extraction.
- **Precision:** `NUMERIC` types do not specify scale/precision in the schema; verify against source DDL if high-precision financial calculations are required.
